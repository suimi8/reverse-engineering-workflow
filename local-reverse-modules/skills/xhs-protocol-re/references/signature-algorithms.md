# 签名算法公式、字段表与验证样本

> 证据基线：`小红书协议登录.har`（521 请求，其中 82 条带 `XYS_`，227 条带响应体；导出时 Cookie 头被剥离）
> 加：2026-08-27 实时链路实测（全新游客上下文）。两类证据在下文分别标注，不合并。

## 一、`XYS_`（`X-s` 头）构造

```
c = sign_path + body_str          # sign_path 必须已含 query
u = MD5(c)                        -> S.x5
p = MD5(sign_path)                -> 只喂 mnsv2，不进 S
v = window.mnsv2(c, u, p)         -> S.x3
S = {"x0": sign_ver, "x1": app_id, "x2": platform,
     "x3": v, "x4": body_type, "x5": u
     [, "x6": {app_id: encSskSign}, "x7": {app_id: encSsk}]}
X-s = "XYS_" + 乱序base64(UTF8(JSON(S)))
X-t = 毫秒时间戳（与 X-s 配对）
```

### 三件套原始实现映射

| 原始 JS | 真实身份 | 复刻 |
|---|---|---|
| `ed.Pu` | CryptoJS MD5 | `hashlib.md5(s.encode('utf-8')).hexdigest()` |
| `ed.lz` | `encodeUtf8` | `s.encode('utf-8')` |
| `ed.xE` | 乱序 base64 | 按下表做 6-bit 编码 |

### 乱序 base64 码表（完整原文，不脱敏）

```
ZmserbBoHQtNP+wOcza/LpngG8yJq42KWYj0DSfdikx3VT16IlUAFM97hECvuRX5
```

编码规则与标准 base64 一致（3 字节 → 4 字符，`=` 补位），只把字母表换成上表：

```python
def _triplet_to_b64(v, T):
    return T[(v >> 18) & 63] + T[(v >> 12) & 63] + T[(v >> 6) & 63] + T[v & 63]
```

`len % 3 == 1` 补 `==`，`len % 3 == 2` 补 `=`，与标准一致。
解码用按位反查即可，**不要**先映射回标准表再交给 `base64.b64decode`——那条路会引入尾部 padding 残留，而按位解码器解出的最后一个字节恒为 `}`（17/17 真实 `x-s-common` 验证）。

### `S` 字段表

| 字段 | 含义 | 取值来源 |
|---|---|---|
| `x0` | seccore 签名版本（原 JS `w.i8`） | 权威值 = `x-s-common.x1`；硬编码仅作回退 |
| `x1` | appId | 权威值 = `x-s-common.x3`（实测 `xhs-pc-web`） |
| `x2` | 平台（原 JS `window[w.mj]`） | 权威值 = `x-s-common.x2`（PC/Windows 实测 `Windows`，原始兜底值 `PC`） |
| `x3` | `mnsv2(c,u,p)` 输出 | 页面实时产出，形如 `mns0301_...` |
| `x4` | body 类型 | `object` / `array` / `string` / `""`（GET 无体） |
| `x5` | `MD5(sign_path + body_str)` | 见下节的关键约束 |
| `x6` | `{appId: encSskSign}` | `buildEncSskSign(u)` 产出，**本模块未复刻** |
| `x7` | `{appId: encSsk}` | 同上 |

> ⚠️ `x0` 是**签名版本**，不是 `webBuild`。同一份报文里 `x-s-common.x1=4.4.1` 与 `x-s-common.x4=6.45.4` 并列出现，二者含义不同、不可互换。把 `x0` 填成 `webBuild` 会直接打坏签名链路。

### `x5` 的关键约束（本模块第一红线）

`x5 = md5(sign_path + body原文)`，**服务端用收到的 body 字节原文重算，不做任何规范化**。

- 浏览器发的是紧凑格式：`{"qr_type":1}`
- 若实现用带空格格式 `{"qr_type": 1}`，算出的 `x5` 完全不同

两种格式**都能过**——只要签名侧与发送侧用的是同一个字符串。这正是危险之处：靠"两边碰巧一致"跑通的实现，任一侧单独改动、或中间层（换 HTTP 客户端 / 代理 / 重试逻辑）重新序列化过 body，签名就静默失效，**症状只是 406，排查方向极易跑偏到 `mnsv2` 或 `x-s-common` 上**。

正确做法：body 只序列化一次，产出的字符串既参与签名又原样发出。

### `x6` / `x7` 结构线索（未复刻，供后续攻关）

| 项 | 实测 |
|---|---|
| 结构 | 均为以 appId 为键的单键字典，值是乱序 base64 |
| `x6` 解码后长度 | 恒 **20 字节**（= HMAC-SHA1 输出长度） |
| `x7` 解码后长度 | 恒 **24 字节** |
| 变化性 | 69 个样本两两不同（每请求都变） |
| `x6` 与 `x1` 的关系 | `x6` 键 == `x7` 键 == 同一条 `S` 的 `x1`，**69/69 无一例外** |

推测起点（**假设，未验证**）：`x6 ≈ HMAC-SHA1(ssk, u)`。因为 `x6` 长度恰是 SHA-1 输出且随 `u` 变化。

分布（HAR 82 样本）：登录链路 `qrcode/create`(2/2)、`userinfo`(33/33)、`qrcode/status`(1/1) **全带**；12 条无 ssk 前缀的**全不带**；另有 1 条 `mns0301_` 的 `user/me` 不带——它是 `activate` 返回后约 230ms 的第一个请求，说明**版本号先翻、`x6`/`x7` 晚一拍**。

> 定性：缺 `x6`/`x7` 时 `qrcode/create` 仍返回 200/code=0，但真实浏览器在登录链路上**每一发都带**。所以这是「**服务端宽容**」，不是「这条链路不需要」。

## 二、`x-s-common` 字段表

同一张乱序码表即可解开，结构恒为 `{s0, s1, x0..x12}`（17 个去重值，17/17 解码成功）。

| 字段 | 实测值 / 含义 |
|---|---|
| `s0` | `5` |
| `s1` | `""` |
| `x0` | `"1"` |
| `x1` | **seccore 签名版本** — HAR 内恒 `4.4.1`；2026-08-27 实时链路已是 `4.4.3` |
| `x2` | 平台 — `Windows` |
| `x3` | appId — `xhs-pc-web` |
| `x4` | **真实 webBuild** — HAR 内恒 `6.45.4`；实时链路已是 `6.45.7` |
| `x5` | **Cookie `a1` 设备指纹**（52 字符） |
| `x6` / `x7` | 恒空 |
| `x8` | 1716~1880 字符的环境指纹 blob |
| `x9` | 与 `x8` 一一对应的校验和，**未解**（crc32 有符号/无符号、adler32、crc32(x5)、crc32(x12) 全部 82 条不中；值有正有负，是有符号 32 位） |
| `x10` | `0` |
| `x11` | `"normal"` |
| `x12` | `"<请求时刻ms>;<引擎下发常量>"` |

### `x5 == a1` 的证据源分列

- **这份 HAR 证不了**：导出时 Cookie 头、`request.cookies`、`Set-Cookie` 全部为空，找不到任何 `a1`。HAR 只能证明 `x5` 恒 52 字符、整份抓包同一个值。
- **实时链路已证**：全新游客上下文，同一 context 里 `a1` 与解出的 `x5` **逐字节相等**。

因此「`x-s-common` 与 `a1` 必须同源」这个隐患**可以直接检测**：解开 `x-s-common` 比对 `x5` 与 Cookie 里的 `a1`，不必再靠注入顺序来赌。
自检必须**只告警不拦截**——宁可发出去也不能把主链路打死。

### `x12` 与 `sign_engine.js` 的挂钩

尾段等于所下发签名引擎里 `getdss()` 的返回常量（观测到 `1787298561512`）。
**78/82 命中**；不中的 4 条正是 `mns0201_` 引导请求，即 `POST /api/sec/v1/scripting` 重新下发引擎那一刻。

> 这比"一字不差"是更强的证据：说明 `x12` 尾段是**引擎身份标识、会随下发轮换**，而不是一个固定常量。头段比尾段晚约 5 天，符合"头 = 请求时刻、尾 = 脚本下发时烧进去的常量"。

## 三、签名参数实时取值（去硬编码）

因为 `x-s-common.x1/x2/x3` 就是权威的 `sign_ver`/`platform`/`app_id`，签名参数应当**从实时 `x-s-common` 读取**，硬编码常量降级为回退值。

设计要点：

- **逐字段回退**：某格脏/缺只退那一格，不牵连其余。
- **只校验形状，不做版本白名单**：版本用 `^\d+\.\d+\.\d+$`、webBuild 用 `^\d+(?:\.\d+)+$`；写死白名单等于把"提前拆雷"又变回硬编码，下次漂移照样中招。
- **脏值宁可回退也不放行**：脏值进签名比用旧版本更糟。
- **`source` 只反映 `sign_ver`**：因为是逐字段回退，`source == 'fallback'` 时其余字段仍可能是 live 值，不要拿 `source` 反推其它字段来源。
- **一次性脚本只解一次**并复用，保证"启动时打印的那份"与"实际签进去的那份"是同一个，杜绝日志说 live、实际用 fallback 的错位。
- **常驻服务绑 `x-s-common` 生命周期**解析（每个赋值点都要覆盖），只在版本变化时打印一行。去重键要用 `(sign_ver, source)` 而非只看 `sign_ver`——线上版本恰好等于硬编码回退值时（`4.4.1` 就是这种情况），"已跟上线上"和"还在拿常量硬猜"在日志里会长得一模一样。

## 四、验证统计

| 验证项 | 结果 |
|---|---|
| 乱序码表解真实 `XYS_` | **82/82** 全部解码成功 |
| `md5(path + postData.text) == 解出的 x5` | **81/82**；差的 1 条是 `POST /api/sec/v1/shield/webprofile`，HAR 导出缺 `postData`（其 `x4=object` 说明本来有 body），属抓包缺失不是算法反例 |
| `x-s-common` 同表解码 | **17/17**（82 条头，17 个去重值） |
| `getdss()` == `x12` 尾段 | **78/82**（4 条不中 = 引擎重新下发那一刻） |
| `x6` / `x7` 长度 | 20 / 24 字节，69 样本两两不同 |
| `x6` 键 == `x7` 键 == `S.x1` | **69/69** |

### 可复现的自测锚点（不含任何凭据）

```
md5('/api/sns/web/v1/login/qrcode/create' + '{"qr_type":1}')
  = f6a462b6b0226d11b4c461e220029951      # 紧凑格式，与浏览器一致
md5('/api/sns/web/v1/login/qrcode/create' + '{"qr_type": 1}')
  = bfca819a8826d79d5f1b14502150d3ca      # 带空格格式，与浏览器不一致
```

把第一条写成断言，并且**让断言走真实代码路径**（调实际的签名前置函数，而不是手写字面量）——否则自测会在实现已经偏离浏览器时仍然全绿。这是本模块踩过的真实坑：文档曾据"手写紧凑串算出的 md5 与真实 `x5` 一致"宣称复刻正确，而当时的实现实际产出的是带空格版本的 `bfca819a…`。

### 端到端验收基线

```
POST /api/sns/web/v1/login/qrcode/create        -> HTTP 200 code=0 success=true
GET  /api/sns/web/v1/login/qrcode/status?...    -> HTTP 200 code=0 code_status=0（带 query）
```

全新游客上下文（无 ssk）时 `mnsv2` 返回 `mns0101_` 前缀，与"版本号随 ssk 状态切换"一致。
